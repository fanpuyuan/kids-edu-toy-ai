# KidsEduToy AI - RAG & 记忆系统设计讨论

本文档用于深入探讨早教机项目的知识库 RAG (检索增强生成) 与 长效记忆 (Long-term Memory) 的实现细节。

## 1. 数据清洗与预处理 (Data Cleaning)
针对儿童教育场景，原始数据往往来自绘本、百科全书或对话记录，直接注入向量库效果较差。

*   **清洗重点**：
    *   **去除杂质**：过滤掉绘本中的页码、版权声明、出版信息等干扰文本。
    *   **语义聚合**：儿童读物往往图多字少，需要人工或由 AI (如 GPT-4o) 辅以“图片描述”，将零散的短句合并为具有完整语义的段落。
    *   **结构化**：针对百科类数据，提取 `主题`, `核心问题`, `通俗解释` 等字段，构建高质量的 QA 对。
*   **讨论点**：我们需要针对哪些特定格式的文件（PDF, Markdown, JSONL）做深度清洗？

## 2. 向量空间与 Embedding 模型
*   **模型选择**：目前推荐 `BAAI/bge-large-zh-v1.5`。
*   **向量空间管理**：
    *   **维度固定**：该模型产生 1024 维向量。如果未来需要更换模型（如换成 OpenAI 的 `text-embedding-3-small`），**必须重建索引**。
    *   **多模型并存方案**：是否需要为一个 Collection 存储多个版本的 Embedding？（通常不建议，复杂度太高，建议在 Collection 名称中带上模型版本）。
*   **讨论点**：是否需要引入“重排序 (Reranker)”增加准确度？（增加显存和延迟，但能显著提高检索精准度）。

## 3. 记忆系统 (Memory System) 深度对比
针对你提到的几种记忆模式，在早教机这种“小模型+高频互动”的场景下，我们的选型建议如下：

| 方案模式 | 实现原理 | 优点 | 缺点 | 适配建议 |
| :--- | :--- | :--- | :--- | :--- |
| **纯 KV 模式 (Key-Value)** | 显式存储 `{"项": "值"}`，如宝宝生日、英雄名。通过代码注入 System Prompt。 | 绝对准确，0 检索延迟，对小模型最友好。 | 无法处理感性的、复杂的往事（如“上次我哭的原因”）。 | **核心必选**。用于存储宝宝姓名、偏好、家庭成员等硬核信息。 |
| **OpenAI/Generative 模式 (如 Mem0 / Zep)** | 使用一个独立的 LLM 代理，自动从对话中提取隐含事实并更新图谱或向量库。 | 极具“生命感”，能记住非常细碎的非结构化信息。 | 逻辑极复杂，非常吃算力（需要一直跑后台提取进程），容易产生“记忆幻觉”。 | **进阶可选**。适合未来算力充足时，用来记录“宝宝的成长点滴”。 |
| **Claude/Long-Context 模式** | 简单粗暴：把几万字的对话历史全部塞给模型（或使用 Summarizer 不断压缩）。 | 开发最快，模型能感知到细微的前后语境。 | 对本地小模型（0.8b/2b）是灾难；上下文太长会导致模型变傻（注意力分散）且推理变慢。 | **不建议**。本地部署必须控制上下文长度（< 2k tokens）。 |

### 我们推荐的组合方案：**“结构化档案 (KV) + 碎片化往事 (Vector)”**

1.  **静态档案层 (JSON/KV)**:
    *   **内容**：姓名、年龄、过敏源、最喜欢的绘本。
    *   **触发**：对话开始时，Gateway 自动读取 `user_profile.json` 注入。
2.  **动态往事层 (Vector Memory)**:
    *   **内容**：过去几天的关键对话片段（如：“昨天聊了恐龙，宝宝很兴奋”）。
    *   **触发**：由 Brain Service 的一个专门节点（Memory Extractor）在对话结束时生成一条摘要，存入 ChromaDB 的 `memory` 集合。
    *   **检索**：当用户提到“昨天”、“上次”等词汇时，触发 RAG 检索这些片段，并作为背景知识喂给模型。

## 4. 数据库与分块 (Vector DB & Chunking)
*   **数据库**：ChromaDB (Local)。
*   **分块**：`RecursiveCharacterTextSplitter`。
    *   **Chunk Size**：500~800 字。
    *   **Overlap**：10% ~ 15%。
*   **讨论点**：针对长篇童话逻辑，是否需要使用“父文档检索 (Parent Document Retrieval)”？即：检索时匹配小块，但喂给模型的是它所在的整个大章节。

## 5. RAG 架构路线思考: 普通 RAG vs GraphRAG
针对本项目的特殊形态（儿童语音互动玩具），我们在架构选型上更倾向于 **普通 RAG (Vector RAG) + 独立的 KV 记忆系统**，而非目前大火的 **GraphRAG**。

*   **普通 RAG (适合本项目的主力方案)**：
    *   **优点**：检索速度极快（毫秒级），算力开销极低（仅使用 Embedding 模型和 ChromaDB）。非常适合儿童常见的**单点事实查询**（“霸王龙吃什么？”）和**特定内容提取**（“给我讲昨天那个三只小猪的故事”）。
    *   **契合点**：早教机的首要指标是**低延迟响应**（儿童的耐心非常短）。加上我们在本地环境使用轻量级的小模型（如 Qwen 0.8B/2B），普通 RAG 的上下文复杂度低，小模型更容易理解和遵循。
*   **GraphRAG (微软架构等)**：
    *   **优点**：极具深度的推理能力，能回答跨文档的全局性问题（“总结这十本书里所有动物的社会关系”）。它通过用 LLM 提取知识图谱（实体-关系）来进行检索。
    *   **缺点 (对本项目的致命伤)**：
        1.  **极度吃算力和时间 (Indexing 瓶颈)**：将文档构建成图谱索引时，需要疯狂调用大模型提取（且通常需要 GPT-4 级别的大模型才能提取出高质量的关系网）。本地跑 `0.8b` 模型来构建 GraphRAG 几乎是不可能完成的任务（准确率极差且极慢）。
        2.  **检索延迟巨大 (查询瓶颈)**：基于图的查询常常需要多跳查找（甚至再次调用 LLM 规划路径），导致回复生成时间动辄增加 10 ~ 30 秒。而在玩具端，按下录音键松手后 3 秒不说话，小孩可能就跑了。

### 结论：记忆与知识分离的务实策略
我们不用 GraphRAG 这么重的架构，而是“解构”它想解决的问题：
*   如果只是想让它**记住宝宝的习惯与信息**：我们不建浩瀚的图谱，只建一张简单的 JSON 表（如 `{"宝宝名字": "小明", "讨厌": "吃青椒"}`）。对话开始前，直接将这些核心 Key-Value 当做 System Prompt 塞给大模型（也就是 **长期记忆的显式挂载**），这样不仅极其稳定，而且0额外检索延迟。
*   如果是**讲故事、查百科**：就用最成熟快速的**普通向量 RAG (ChromaDB)**。

## 6. 最终决议方案：Hybrid RAG + 层次化 Markdown 记忆

经过深度探讨，我们决定弃用沉重的 GraphRAG，转而采用一种更适合早教机硬件且更具透明性的“**复合型检索与记忆架构**”。

### 6.1 检索架构：OpenClaw 流派 (Hybrid Search)
为了兼顾“模糊语义理解”和“精准关键词匹配”，我们不纯靠向量：
*   **Vector Search (ChromaDB + BGE-large-zh)**: 负责理解语义。例如宝宝问“那个恐龙灭绝的事”，即便文档里写的是“白垩纪灾变”，向量检索也能找对。
*   **BM25 (Rank-BM25 库)**: 负责关键词匹配。例如宝宝问“小猪佩奇”，只要文档里出现了这个词，BM25 就能以极高的置信度将其召回。
*   **融合算法**: 混合重排序 (RRF)。我们使用 Llamaindex 的 `QueryFusionRetriever` 来实现。
    *   *避坑指南*：`QueryFusionRetriever` 默认会强依赖 OpenAI 来改写 Query。由于本服务专注于纯检索（生成侧在大脑服务进行），必须在初始化时传入 `num_queries=1`（表明不重写）并注入一个 `MockLLM()` 作为占位符，从而绕过强制性的 API Key 校验逻辑，避免服务引发 `500 Internal Server Error` 崩溃。

### 6.2 记忆架构：Claude 流派 (三层结构 Markdown)
我们将记忆从单一数据库中解放出来，存储为三个层级的本地 Markdown 文件，这些文件既是存储，也是上下文注入的模版：

1.  **Level 1: `SYSTEM.md` (核心基座)**
    *   **内容**：角色设定（你是谁）、对话禁忌（不准聊暴力）、核心指令。
    *   **更新频率**：极低（由开发者或家长在网页端一次性设定）。
2.  **Level 2: `FAMILY.md` (动态画像)**
    *   **内容**：宝宝的姓名、年龄、家人关系、喜好、过敏源。
    *   **更新频率**：中等。
    *   **来源**：用户在 Web UI 手动填写 + 偶尔由 AI 在对话结束时提取关键更改。
3.  **Level 3: `SNAPSHOT.md` (会话快照)**
    *   **内容**：最近几天的关键事件摘要（如“今天宝宝学了一句唐诗”）。
    *   **更新频率**：高（每次完整对话结束后自动生成）。
    *   **存储机制**：这些快照会被 `BM25 + Vector` 循环检索。

### 6.3 数据清洗与入库 SOP
*   **格式强制要求**：所有上传的绘本、知识库，在进入 Embedding 前，先由一个“清洗脚本”将其转换为清爽的 Markdown 格式（去除页码、广告、乱码）。
*   **语义保护**：采用 `RecursiveCharacterTextSplitter`，严格按照标题 > 段落 > 标点的优先级切分，确保 Chunk 不会切断关键语义。

### 6.4 异构文档解析策略 (Document Parsing Strategy)
针对用户上传的多种格式文档（`.pdf`, `.docx`, `.txt`, `.md`），我们会在 **Pipeline 1 (Ingestion)** 的最前端建立一个“**统一适配器 (Unified Parser Adapter)**”：
1.  **分发路由**：根据文件后缀，调用专门的 Loader：
    *   `.txt` / `.md`: `TextLoader` / `UnstructuredMarkdownLoader` (直接读取)。
    *   `.pdf`: `PyMuPDFLoader` (极速提取 PDF 文本与页码结构)。
    *   `.docx`: `Docx2txtLoader` (提取 Word 文本)。
2.  **“通天塔”转换 (Normalize to Markdown)**：不管什么格式进来，Loader 提取后，第一步全部“强制格式化”为我们系统底层的通用 Markdown 结构。例如把 PDF 的大号加粗字体转为 `# 标题`，普通段落转为正文。
3.  **元数据打标 (Metadata Injection)**：在解析每一页/每一段时，系统会自动打上标签 `{"source": "十万个为什么.pdf", "page": 15}`。这在被切成数百个 Chunk 后，依然能精确溯源（Citation）。
4.  *扩展储备*：由于早教机多为绘本（图多字少），未来如果算力允许，此处可接入 `Qwen-VL-Chat` (多模态模型) 进行 OCR 和“看图说话”，提取图片文字再转为 Markdown 入库。现阶段仅提取纯文本以保稳定。
